# FT8CN Roadmap 与可派发 TODO

> 基线：`codex/v0.93.005-integration`（P0 集成中，尚未完成最终 AVD/真机门禁）<br>
> 日期：2026-08-01<br>
> 原则：稳定性 > 兼容性 > 性能与省电 > 新功能<br>
> 范围：本路线只描述要解决的问题、验收方法和派发边界，不代表任务已经实现或验证

## 1. 状态定义

| 状态 | 含义 |
|---|---|
| 已确认缺陷 | 代码路径已经能证明契约错误，不需要先靠猜测立项 |
| 较高概率风险 | 代码存在明显风险，但仍需自动化或运行证据确认影响 |
| 代码正向变化 | 已看到合理改进，但效果或完整性仍需测量 |
| 待自动验证 | 需要 JVM、Instrumented、故障注入或流水线验证 |
| 待真机验证 | 需要 Android 设备或真实电台 |
| 待性能验证 | 需要先建立基线，再做相对对比 |
| 完成 | 修复、自动化、文档和所需真机门禁全部闭环 |

一个任务可以同时有多个状态，例如“已确认缺陷 / 待自动验证 / 待真机验证”。

## 2. 执行规则

1. 一次只解决一个可解释的问题，每个提交能独立回滚；
2. P0 未完成前不扩大新功能范围；
3. 先补能复现问题的自动化，再做最小修复；
4. 不把构建成功、模拟器成功或代码阅读写成 HIL；
5. 性能任务先建立基线，目标以相对改善和不退化为主；
6. 不承诺未经测量的固定绝对功耗、温度或耗时；
7. 真机测试必须记录版本、设备、电台、连接方式、时长和日志；
8. 改动核心时隙、PTT、网络包和日志事务前，先列出调用方；
9. `MainViewModel` 和 `GeneralVariables` 只允许小步迁移，禁止一次性大重构；
10. 每个任务完成后更新本文件状态和 `HANDOFF.md`。

## 3. 稳定版总门禁

稳定版候选至少满足：

- 所有 P0 完成；
- `assembleDebug`、JVM 单测、Instrumented 核心用例、lint 基线和 `assembleRelease` 有明确结果；
- Release APK 使用固定正式证书，能覆盖升级上一稳定版；
- 解码活跃任务始终不超过 1；
- 生命周期进入退出 100 次无线程、Observer、Timer 或 Socket 增长；
- 网络包任务 10 万次无快照串扰；
- TCP EOF 后 200ms 内退出读取循环，断开回调只发生一次；
- 连接切换和自动重连 100 次无残留轮询和错误 PTT；
- WiFi 网络模式完成真实接收、解码和一次完整 QSO；
- 连续挂机 2 小时无崩溃、无解码停止、无持续线程增长；
- 关键场景完成 30 分钟相对功耗、温升和解码耗时对比；
- 所有未覆盖设备和连接方式在发布说明中列为验证边界。

这些次数是回归门禁，不是对用户设备性能的承诺。

## 4. P0：发版前必须完成

### P0-A 共享执行器所有权与永久 Observer

**状态**：已实现并集成 / JVM 与编译门禁通过 / 待最终 AVD / 待真机验证

**为什么要改**

- `FT8TransmitSignal` 使用进程级共享 `AppExecutors.decoding()`，却在组件 `stop()` 时调用 `shutdown()`；
- `GeneralVariables.mutableVolumePercent.observeForever(...)` 没有在停止时移除；
- 退出一个组件可能关闭其他任务要使用的共享池，反复创建 ViewModel 会累积 Observer。

**如何改**

1. 明确 `AppExecutors` 为进程级所有者，业务组件不得关闭共享 executor；
2. `FT8TransmitSignal` 保存自己提交的 `Future`，停止时只取消自己的任务；
3. 保存音量 `Observer` 引用，在 `stop()` 中成对 `removeObserver`；
4. `stop()` 设计为幂等，重复调用不报错、不重复 PTT OFF 回调；
5. 补一条代码规则：只有 `Application` 级关闭流程可以 shutdown 共享池。

**用户价值**

- 退出、旋转、重进应用后仍能正常发射；
- 降低后台对象和线程累积导致的长时闪退、发热和异常状态。

**涉及范围**

- `AppExecutors`
- `FT8TransmitSignal`
- `MainViewModel.onCleared`
- `GeneralVariables.mutableVolumePercent`

**自动化验收**

- 同一进程中创建和清理发射组件 100 次；
- 共享 decoding executor 始终可提交新任务；
- Observer 数量不随循环增长；
- `stop()` 连续调用多次结果一致；
- 活跃发射任务能取消，其他共享任务不受影响。

**真机/性能验收**

- Android 设备进入退出主界面 100 次；
- 对比前后线程数、Observer、内存和空闲 CPU，无持续增长；
- 最少完成一次退出后重新进入并发起接收/发射流程。

**依赖**

- 无，可独立开始；
- 建议先建立线程和 Observer 计数测试工具。

**风险与回滚**

- 风险：取消任务时误触发两次 PTT OFF；
- 回滚：保留旧 stop 行为的单提交回滚点，但不得保留 shutdown 共享池；
- 发射中的取消必须以 PTT 回到 OFF 为硬条件。

### P0-B 任务快照串扰与 Radio TCP EOF 忙循环

**状态**：已实现并集成 / JVM 与编译门禁通过 / 待最终 AVD / 待真机验证

**为什么要改**

- Radio UDP、ICOM UDP、Radio TCP 和 `MainViewModel` 的 QTH/发送路径存在复用可变 Runnable 或先改字段再提交任务的模式；
- 排队、并发或重试时，早先任务可能读到后一次请求覆盖的数据；
- Radio TCP 读取到 EOF 后若不退出，可能形成快速空循环、重复断开回调和高 CPU。

**如何改**

1. 每次提交创建不可变任务快照；
2. 数据包复制必要字段，禁止任务从共享可变字段读取请求参数；
3. 对高频数据包采用有界单消费者队列或序号化通道；
4. TCP `read() == -1` 立即结束循环、关闭资源并只通知一次断开；
5. 对断开、异常、主动关闭统一一个幂等终态。

**用户价值**

- 避免错台发送、错误 QTH、数据包内容错位；
- 网络断开后手机不再空转发热；
- 重连结果更可预测。

**涉及范围**

- `RadioUdpClient`
- `IcomUdpClient`
- `RadioTcpClient`
- `MainViewModel.GetQTHRunnable`
- `MainViewModel.SendWaveDataRunnable`
- 相关 connector 回调

**自动化验收**

- 连续提交 10 万个带唯一序号的任务，无内容串扰、重复或越序；
- 队列满时行为可观测且符合策略；
- EOF 故障注入后 200ms 内退出；
- 断开回调只触发一次；
- 主动关闭、异常关闭和远端 EOF 都能重复执行而不报错。

**真机/性能验收**

- WiFi 连接断开和恢复循环；
- 连接切换/重连 100 次；
- EOF 后 CPU 快速回到空闲基线；
- 真实网络音频和 CAT 数据不出现错序症状。

**依赖**

- 可使用假的 Socket、队列和 Connector；
- 与 P0-A 的任务所有权规范保持一致。

**风险与回滚**

- 风险：复制数据增加少量分配；
- 优先保证正确性，再通过对象池或固定缓冲优化；
- 每个通道独立提交，便于按通道回滚。

### P0-C 配置加载完成事件

**状态**：已实现并集成 / 编译门禁通过 / 待最终 AVD / 待真机验证

**为什么要改**

`DatabaseOpr.getAllConfigParameter()` 逐行向主线程回调，最后再回调一次 `null`；`MainActivity.InitData()` 却把每一行都当成全部配置完成，导致重复 GPS、写配置、导航和 USB 选择。

**如何改**

1. 明确拆分 `onConfigItem` 和 `onConfigLoadCompleted`；
2. 只在完成事件设置 `configIsLoaded`；
3. GPS、发射时隙设置、首次导航和 USB 恢复只执行一次；
4. 配置解析错误按字段回退默认值，并记录字段名；
5. Activity 销毁后不再执行旧实例回调。

**用户价值**

- 启动更快；
- 首次设置、旋转和 USB 自动恢复不再重复弹出或跳转；
- 避免配置加载时序造成的错误连接参数。

**涉及范围**

- `DatabaseOpr.getAllConfigParameter`
- `OnAfterQueryConfig`
- `MainActivity.InitData`
- 配置读取测试

**自动化验收**

- 空配置、完整配置、损坏字段、旋转中加载四种场景；
- 完成事件严格一次；
- GPS、导航、USB 恢复严格一次；
- 每个字段加载后最终快照正确；
- Activity 销毁后无旧回调操作 UI。

**真机/性能验收**

- 首装设置页只进入一次；
- 已配置用户不误进设置页；
- USB 已连接时设备选择只触发一次；
- 比较启动关键路径耗时，不允许明显退化。

**依赖**

- 无；
- 建议最先修复，便于后续真机测试稳定启动。

**风险与回滚**

- 风险：完成事件漏发导致启动遮罩不消失；
- 保留 5 秒 UI 兜底仅作为诊断，不作为正常完成机制；
- 回滚时不能恢复逐行完成动作。

### P0-D FT8 解码单飞与状态终态

**状态**：已确认缺陷 / 较高概率风险 / 待自动验证 / 待真机验证

**为什么要改**

- 每个时隙直接创建新解码线程，没有阻止上一轮解码未完成时再启动；
- 空结果会提前返回，`mutableIsDecoding` 不能复位；
- native 异常也没有统一终态；
- 慢设备或深度解码可能重叠，造成 CPU 峰值、乱序消息和时隙错误。

**如何改**

1. 使用专用单线程解码协调器；
2. 活跃解码任务最多一个；
3. 定义上一轮未完成时的策略：记录并跳过、取消或降级，不能并行；
4. 在统一 `finally` 中复位状态、耗时和诊断；
5. 空结果也要发布“本轮完成”和零计数；
6. 对过期时隙结果设置 epoch/slot，禁止晚到结果驱动当前自动通联。

**用户价值**

- 无信号时界面不再一直显示解码中；
- 慢设备和深度解码更稳定、更省电；
- 自动回复不会使用过期时隙结果。

**涉及范围**

- `FT8SignalListener`
- `MainViewModel.afterDecode`
- `AppExecutors` 或新的 `DecodeCoordinator`
- 自动 QSO 调用入口
- JNI 异常处理

**自动化验收**

- 空结果、异常、超时、慢解码、连续时隙；
- 任意时刻活跃解码任务 `<= 1`；
- 每次 before 都有且只有一个终态；
- 过期结果不进入自动候选；
- 深度解码超过预算后可控停止。

**真机/性能验收**

- 真实音频连续解码；
- WiFi 发射后恢复接收；
- 2 小时挂机无解码停止；
- 记录平均、P95 解码耗时、跳过时隙数、CPU 和温升；
- 只要求相对改善或不退化，先建立基线。

**依赖**

- P0-A 的执行器所有权；
- 可与 HamRecorder 故障注入测试共用假音频。

**风险与回滚**

- 风险：过严单飞会跳过本可完成的深度解码；
- 首版优先快速解码时隙正确，深度解码作为可降级功能；
- 保留关闭深度模式的回滚开关。

## 5. P1：稳定、性能与省电主线

### P1-01 真实录音状态与移除主线程 sleep

**状态**：已确认缺陷 / 待自动验证 / 待真机验证

**为什么要改**：`HamRecorder.isRunning` 与底层 `AudioRecord` 脱节；前台服务启动路径在主线程 sleep。失败后可能显示“正在录音”并持续解零样本，启动也会卡顿。<br>
**如何改**：增加 started/failed/stopped 状态回调；状态只由真实录音会话推进；用服务 ready 回调替代 sleep；加入有限退避重启。<br>
**用户价值**：录音故障可见、可恢复，启动更顺畅，无效解码更少。<br>
**涉及范围**：`MicRecorder`、`HamRecorder`、`AudioForegroundService`、录音状态 UI。<br>
**自动化验收**：权限拒绝、初始化失败、DEAD_OBJECT、停止/恢复；状态与底层一致；主线程无 sleep。<br>
**真机/性能验收**：权限首次授予、USB/蓝牙音频切换、发射后恢复；记录启动耗时和无效解码次数。<br>
**依赖**：P0-D 解码终态。<br>
**风险/回滚**：重试可能抢占系统音频；限制次数并允许用户手动恢复。<br>

### P1-02 Rig / ConnectionSession 统一生命周期

**状态**：已确认缺陷 / 待自动验证 / 待真机验证

**为什么要改**：Rig 构造即启动 Timer，断开时缺少统一取消。FT-710 为避免 USB 复合设备冲突已禁用 `CableSerialPort` 的 USB read loop，却继续复用 `YaesuDX10Rig`，每 2 秒发送 FA/RM 查询；只写模式没有回包，Timer 也没有 cancel。这一无响应轮询和生命周期错误是确认缺陷；实际耗电和不同 FT-710 的 HIL 影响仍待测量。证据：`CableSerialPort.java:125-128,241-245`、`YaesuDX10Rig.java:27-46,175-190`。<br>
**如何改**：引入小型 `ConnectionSession`；明确 create/connect/active/disconnect/closed；统一持有并取消 Timer、Handler callback、Socket 和读循环；FT-710 只写模式作为明确 capability，禁止启动依赖回包的 FA/RM 轮询。保留已有现场 A/B 支持的 USB CAT write-only 核心，不把修 Timer 变成回滚只写方案。<br>
**用户价值**：切台和重连不积累唤醒，不出现旧连接控制新电台。<br>
**涉及范围**：`BaseRig`、各 Rig Timer、Connector、FT-710 路径、`MainViewModel.connectRig`。<br>
**自动化验收**：连接切换/重连 100 次；每个会话只有一组轮询；close 幂等；旧会话不能回调新会话。<br>
**真机/性能验收**：USB 拔插、蓝牙断开、WiFi 重连；比较空闲线程、唤醒和 CPU。<br>
**依赖**：P0-A、P0-B。<br>
**风险/回滚**：统一关闭可能改变少数机型顺序；按机型小步迁移。FT-710 回滚只能回滚新会话管理实现，不得恢复已被现场 A/B 证实会破坏 USB 音频共存的 read loop。<br>

### P1-03 亮屏三档策略

**状态**：待产品确认 / 待性能验证

**为什么要改**：主界面和地图当前无条件常亮，可能成为最大耗电来源。<br>
**如何改**：提供“跟随系统”“仅操作/发射时保持亮屏”“始终亮屏”三档；默认值先通过测试确定；发射结束后可靠释放。<br>
**用户价值**：挂机时更省电，同时保留户外监看需求。<br>
**涉及范围**：`MainActivity`、`GridTrackerMainActivity`、设置持久化、发射状态。<br>
**自动化验收**：三档切换、旋转、前后台、发射开始结束；Window flag 始终符合策略。<br>
**真机/性能验收**：三档各做关键场景 30 分钟相对功耗和温升对比；屏灭后不丢时隙。<br>
**依赖**：真实录音和后台运行路径稳定。<br>
**风险/回滚**：屏灭可能触发厂商省电限制；保留“始终亮屏”作为兼容回滚。<br>

### P1-04 瀑布图与 FFT 热路径

**状态**：代码正向变化 / 待性能验证

**为什么要改**：已有双位图和限帧，但当前仍进行整图复制，FFT 入口和数组分配仍可能增加 CPU、内存带宽和 GC。<br>
**如何改**：先在 FFT 入口限帧；复用数组；再把整图复制改为 front/back 交换；最终评估环形行缓冲。<br>
**用户价值**：长时间看瀑布图时更流畅、更少发热。<br>
**涉及范围**：`SpectrumListener`、`SpectrumFragment`、`SpectrumView`、`WaterfallView`、JNI FFT。<br>
**自动化验收**：尺寸变化、快速旋转、后台绘制；无 recycled bitmap；帧请求有界；数组分配可统计。<br>
**真机/性能验收**：30 分钟瀑布页面对比 CPU、GC、温升和掉帧；解码耗时不退化。<br>
**依赖**：性能观测工具。<br>
**风险/回滚**：缓冲交换可能引入撕裂；分“入口限帧→复用→交换→环形缓冲”四步提交。<br>

### P1-05 XieGu 50pps 空闲与不可重启

**状态**：较高概率风险 / 待自动验证 / 待真机验证

**为什么要改**：常驻发送线程可能在空闲时仍按 50pps 唤醒，停止后的 Runnable/Executor 状态也可能无法再次启动。<br>
**如何改**：用阻塞条件等待待发数据；每次发送会话拥有独立、可重启状态；停止后资源可重新创建。<br>
**用户价值**：协谷网络模式空闲更省电，断开重连后仍能发送。<br>
**涉及范围**：`XieGuAudioUdp`、X6100 Connector、PTT/音频发送。<br>
**自动化验收**：空闲时无 20ms 唤醒；start-stop-start 可用；停止和断开幂等。<br>
**真机/性能验收**：协谷设备空闲、发射、停止、重连；比较空闲 CPU 和功耗。<br>
**依赖**：P0-B 任务快照。<br>
**风险/回滚**：条件唤醒时序错误会丢首包；保留序号和首包测试。<br>

### P1-06 网络总超时与有界上传队列

**状态**：较高概率风险 / 待自动验证

**为什么要改**：单独 connect/read timeout 不能限制整个请求；QSO 连续完成时直接创建线程或无界排队会积压。<br>
**如何改**：定义 GET/POST 总截止时间；统一取消；第三方上传采用有界串行队列、去重和可观测失败。<br>
**用户价值**：弱网不会长期占线程，日志上传失败不会拖慢通联。<br>
**涉及范围**：`ThirdPartyService`、`MainViewModel` 上传入口、HTTP 客户端辅助类。<br>
**自动化验收**：连接慢、响应慢、永不结束、半包、HTTP 错误；总超时可控；队列满按策略处理。<br>
**真机/性能验收**：弱网、断网、恢复网络；QSO 主链不被上传阻塞。<br>
**依赖**：P0-A 执行器所有权。<br>
**风险/回滚**：超时过短影响自建服务器；使用可配置合理默认值并记录阶段耗时。<br>

### P1-07 数据库 N+1 与索引

**状态**：较高概率风险 / 待性能验证

**为什么要改**：呼号、QTH、日志和统计存在逐条查询路径，大日志量下可能放大 IO；索引覆盖不完整。<br>
**如何改**：先用查询计数和 `EXPLAIN QUERY PLAN` 建基线；批量查询或 JOIN；只增加有证据的索引；事务批量写入。<br>
**用户价值**：日志多时列表、统计、导入和启动更快。<br>
**涉及范围**：`DatabaseOpr`、`CountDbOpr`、日志列表、呼号/QTH 补充。<br>
**自动化验收**：构造小、中、大数据集；结果一致；查询次数明显下降；迁移可重复。<br>
**真机/性能验收**：大日志库启动、翻页、统计、导入对比；不承诺测量前的固定耗时。<br>
**依赖**：准备脱敏基准数据。<br>
**风险/回滚**：额外索引增加写入和空间；每个索引独立迁移并可删除。<br>

### P1-08 SWL HashTable 去重空实现

**状态**：已确认缺口 / 待自动验证

**为什么要改**：SWL 去重依赖结构中存在空实现，重复消息或 QSO 可能进入后续统计和日志。<br>
**如何改**：先定义去重键、时间窗口、波段和时隙语义；实现后用确定性样本验证。<br>
**用户价值**：SWL 记录和统计更可信。<br>
**涉及范围**：SWL QSO 识别、HashTable/去重结构、数据库写入。<br>
**自动化验收**：同消息重复、跨时隙、跨波段、弱信号重复、合法相似消息；只去除定义内重复。<br>
**真机/性能验收**：真实监听样本对比去重前后记录；性能不影响每时隙解码。<br>
**依赖**：产品确认去重语义。<br>
**风险/回滚**：过度去重会丢合法记录；默认保守并保留诊断计数。<br>

### P1-09 JTDX priority 自动候选边界

**状态**：已确认功能缺陷 / 待自动验证 / 待真机验证

**为什么要改**：`afterDecode` 先调用 `findIncludedCallsigns`，随后才由异步呼号查询写入 priority。`findIncludedCallsigns` 又依赖 `NEW_DXCC`、`NEW_BAND`、`RARE_DX`，因此这些优先级在首次处理时必然漏选。证据：`MainViewModel.java:330-368,542-550`、`CallsignDatabase.java:99-122,149-200`。<br>
**如何改**：把“视觉排序”和“自动候选策略”分开；为每条消息生成稳定时隙快照；priority 异步完成后，把符合条件的消息补入当前候选；补入操作必须幂等去重，且过期时隙结果不得驱动发射。<br>
**用户价值**：高亮更有用，但不会意外呼叫错误目标。<br>
**涉及范围**：消息优先级、列表排序、`findIncludedCallsigns`、自动呼叫。<br>
**自动化验收**：构造首次为 `NONE`、异步后变为 `NEW_DXCC`、`NEW_BAND`、`RARE_DX` 的消息；priority 完成后均补入候选；重复回调只保留一条；过期消息不参与；同一批消息不同 UI 排序下候选一致。<br>
**真机/性能验收**：监听多台 CQ 环境，人工核对候选和实际发射目标。<br>
**依赖**：P0-D 时隙 epoch。<br>
**风险/回滚**：补候选可能改变首次自动选择；以稳定时隙快照、幂等去重和 epoch 失效保护收窄影响。若需止损，仅关闭“异步完成后补候选”开关，不回滚 priority 显示，也不允许过期结果进入发射路径。<br>

### P1-10 Wavelog station ID 精确匹配

**状态**：已确认功能缺陷 / 待自动验证

**为什么要改**：当前对 JSON 正规化后使用 `contains` 判断数字 ID，目标 station ID `1` 会假匹配响应中的 `123`，使连接测试返回错误成功。证据：`ThirdPartyService.java:256-268`。<br>
**如何改**：使用 JSON 结构解析；按精确字段和类型匹配；兼容 Endpoint 差异但不猜测字段。<br>
**用户价值**：连接测试和上传写入正确站点。<br>
**涉及范围**：`ThirdPartyService`、Wavelog/Cloudlog Endpoint 识别、设置页。<br>
**自动化验收**：明确覆盖目标 `1` 与响应 `123` 不匹配；覆盖数字/字符串 `1` 精确匹配、多个相似 ID、字段顺序变化、缺失字段和错误 JSON。<br>
**真机/性能验收**：至少一个真实 Wavelog 实例完成连接测试和一条受控日志上传。<br>
**依赖**：可用的脱敏响应样本。<br>
**风险/回滚**：不同版本 JSON 结构差异；保留明确版本适配，不回退到 contains。<br>

### P1-11 ConfigFragment view binding 生命周期

**状态**：较高概率稳定性风险 / 待自动验证

**为什么要改**：Fragment View 销毁后仍持有 binding 或后台回调操作旧 View，旋转和快速导航可能泄漏或崩溃。<br>

**用户价值**：设置页旋转、返回和权限回调更稳定。<br>
**涉及范围**：`ConfigFragment`，并顺带核对同模式 Fragment。<br>
**自动化验收**：快速进入退出、旋转、后台任务完成后返回；旧 View 不被访问。<br>
**真机/性能验收**：设置页反复切换和旋转；内存不持续增长。<br>
**依赖**：无。<br>
**风险/回滚**：过早置空导致合法回调被丢弃；状态写 ViewModel，View 只负责展示。<br>

### P1-12 HTTP 日志服务按需启动

**真机/性能验收**：同一局域网浏览、导入、导出；比较未使用日志功能时的线程和唤醒。<br>
**依赖**：日志导入任务生命周期。<br>
**风险/回滚**：服务关闭过早中断大文件导入；进行中任务持有明确 lease。<br>

### P1-13 性能与故障可观测性

**状态**：待实现 / 待性能验证

**为什么要改**：当前“大幅降温”“卡解码”等结论缺少统一指标，难以区分设备、网络和代码原因。<br>
